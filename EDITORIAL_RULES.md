# DATA C0RE — EDITORIAL RULES

Persistent rules for all future portfolio work. Read together with `PROJECT_AI_CONTEXT.md` before editing the site.

## Hard rule: never explain the website strategy to the visitor

Public copy must never describe the portfolio's internal editorial strategy, information architecture or curatorial logic.

Forbidden public-facing patterns include sentences such as:
- "Case studies first; the full history stays in the archive."
- "Work contains the strongest projects while Archive keeps prototypes."
- "This page gathers..."
- "This section exists to..."
- "Research is separated from realized work so that..."

These are internal design decisions, not visitor-facing content.

The interface itself must make the hierarchy obvious through naming, ordering, visual emphasis and links.

## Avoid page duplication

Do not create multiple editorial pages that restate the same identity, capabilities or project information.

Preferred model:
- Home = immediate identity + proof + selected contexts + capabilities + next actions.
- Archive = complete project index, including realized work and clearly labelled R&D / studies / simulations.
- One canonical detail page per project/case study.
- CV = professional chronology, roles, institutions, skills and experience.
- Contact = secure contact form.

Home and Archive may contain short navigation teasers for a project, but the substantive project narrative must live on one canonical project page only.

Avoid separate top-level Work, About, Services or Lab pages when their content is already covered by Home, Archive, CV or individual project pages.

## Visitor test

A visitor should be able to answer within seconds:
- What does DATA C0RE do?
- What has DATA C0RE actually done?
- Where / with whom?
- What technical capabilities are relevant?
- Where do I click for one project, the full archive, professional history or contact?

Do not make the visitor learn the site's taxonomy before seeing the work.
